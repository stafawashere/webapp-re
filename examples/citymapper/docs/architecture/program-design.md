# Program design

The planned `/citymapper` program as of stage 2. The machine-readable plan is
[plan/plan.json](../../plan/plan.json), rendered for people as [plan/plan.md](../../plan/plan.md), both
generated by `tools/plan/build_plan.py`. This page explains the shape and the reasons; it does not
repeat every schema.

## Package

Python uv project at `program/`, package `citymapper_client`, console script `citymapper`, following
`plugin/references/program-architecture.md` (session, transport, pacing, classify,
errors, models, endpoints, capabilities, registry, cli, offline tests from synthetic fixtures, the
provenance gate). JSON on stdout by default, `--format table` for people, JSON errors on stderr with
the reference exit codes. The plan adds a `NotFound` failure class for unknown stops, lines and
cities (a 404 page or an empty result), mapped to an exit code in stage 3.

## City as input

Every command that talks to the site takes `--city`, which may be a region slug (`nyc`), a region id
(`us-nyc`), a city slug (`jersey-city`, resolved to its region) or a name (`New York`, matched against
names and aliases). The resolver reads a catalogue cached under `var/cache` for 7 days, built by
`list-cities` from one page's `window.citymapper` globals ([D4](../decisions/decisions.md#d4-region-config-from-html-not-an-api)).
`get-city` adds the region config (nearby modes, brands, bounding box, timezone) from
`/resource/region-info/{region_id}`. Coordinates outside the region's bounding box are rejected before
any request, mirroring the web client's out-of-bounds check.

## Places as input

`from`, `to` and `near` accept `lat,lng` or text. Text is resolved with `search-places` in the same
city (the first non-heading result with coordinates), which costs one extra request and is reported
in the output's `from` and `to`. Times (`--depart-at`, `--arrive-by`) accept ISO or `HH:MM` in the
city's timezone and are sent as ISO UTC (`departure_time`, `arrival_time`), as the web client does.

## Command design choices

- One command per sentence a user would say, so `get-departures` hides the three departures feeds
  behind `stopinfo`'s `departure_api` ([pattern](../../knowledge/patterns/quirk-departure-api-per-brand.md)),
  and `get-disruptions` fills the `{n}` placeholders from `replacements` into readable text.
- Journeys return the planner's `signature` so `get-journey-times`, `get-journey` and `share-journey`
  can be chained.
- No command polls: one snapshot per call (brief: no polling loops), even where the web page re-polls
  every 30 s or 2 minutes.
- `plan-walk` depends on `/api/7/walk` and keeps `/api/1/walk` as a fallback dependency so the scope's
  walk capability maps fully.

## Writes

Every write has `--dry-run` (prints the exact request) and needs `--yes`.

- Round trip (account-writes tier): runs live only under the standing overnight grant and only with a
  session: read, write, read back, run the exact inverse, read back to the starting state.
  `save-journey` may notify your phone, a side effect its inverse cannot undo; stage 3 treats it as an
  approval write if the save sends a push ([D9](../decisions/decisions.md#d9-save-journey-is-a-round-trip-unless-it-pushes)).
- Approval (approval tier): never sent without your approval of the exact dry-run call; listed in
  `PENDING-APPROVALS.md`.

## Not planned

Sign-in (magic link, Google, Facebook), password reset and sign-up confirmation, and analytics
telemetry, with reasons in [plan.md](../../plan/plan.md#not-planned) and
[D8](../decisions/decisions.md#d8-what-is-not-planned).

## Open reverse-engineering budget

58 open steps, budget 116 requests (from `check_plan.py`): two replays for each observed endpoint a
command depends on, and a first live observation for each bundle-only endpoint. The brief allows
exceeding it, but never faster than the pacer.

After stage 3 the plan shows 22 open steps and a budget of 44 requests; all of them need your
session or a public slug. What was built from this design is in
[implementation/program.md](../implementation/program.md).
